  arithmetic, controllers and defaults remain compatible. The [baseline report](docs/benchmarks/lp-baseline-gpup2.md)
  records 144 trials and 173.148 GPU seconds; CUDA certified only the two small
  witness cases. No low-precision recipe is promoted.
- Accurate observed LP device-buffer peak and per-call kernel launch counts for
  study accounting; the old launch counter omitted the second Halpern launch.

- The approved [GPU LP precision roadmap](docs/plans/gpu-lp-precision-roadmap.md),
  GPUP-0 through GPUP-10 backlog slices, draft numerical/experiment specifications,
  and ADR-0012/ADR-0013. The selected objective is certified single-solve latency
  with an eight GPU-hour first experiment campaign and component/interaction
  ablations before recipe selection. Repeated-solve throughput and full MILP search
  performance are separate future tracks. That initial planning change shipped
  no mixed-precision backend, experiment result, or new default; GPUP-2 evidence
  is recorded separately above.
- A recorded reduced-cost cancellation defect in the existing LP certification,
  with an exact binary64-coefficient counterexample and GPUP-1 repair prerequisite.
  The earlier certification claims below describe the intended contract; the
  GPUP-1 repair recorded below resolves this case with exact-arithmetic regressions.

- `optimizer-lp`, the host half of SPEC-0011: the canonical linear-program form,
  the fixed reduction order, and diagonal preconditioning. It takes no device
  dependency and adds no third-party crate. Being device-free is the point rather
  than a convenience: this is the oracle the LP kernels are checked against under
  requirement 24, and an oracle that needed the thing it checks would establish
  nothing. It is not the fallback path -- requirement 26 keeps that the pinned CPU
  backend, because falling back to a second implementation written to match the
  kernel would make an agreement test compare a component with itself.

  The constraint matrix is held in both row-major and column-major form so that
  neither product needs atomic accumulation, which is a determinism requirement
  before it is a performance one: floating-point addition is not associative, so an
  atomic reduction would make a result depend on how the hardware scheduled it.
  Reductions use one shared partition and tree order, defined once here for both
  engines rather than restated by the kernel.
- Host certification of a dual bound, under SPEC-0011 requirements 11 to 13. A
  bound is produced only by a host-side procedure in `f64` that recomputes the
  reduced costs from the original model's own coefficients and evaluates weak
  duality. It reads no residual, no norm and no objective the device computed, so
  it cannot be checking the device against itself.

  The bound is valid for an arbitrary multiplier vector, including one nowhere near
  optimal: a bad guess makes the bounded terms small, so the bound is weak, but it
  cannot make the bound invalid. Where a variable's bound is infinite on the side
  its reduced cost needs, no finite number is a bound and none is reported --
  the refusal names the variable rather than clamping to something large.

  A conservative rounding allowance is subtracted, because the underlying argument
  is exact in the reals and a `f64` sum that landed above the true value would be a
  bound stronger than the evidence supports.
- `HostLpBackend`, a first-order linear programming backend that runs entirely on
  the host, under SPEC-0011 requirements 24 and 25. It refuses any model with a
  discrete variable as `Unsupported` before doing any work, because a first-order
  method has no branch and bound and a relaxed answer to a discrete question would
  be wrong rather than refused. `Optimal` requires a candidate `Model::evaluate`
  accepted and a certified bound to close, so two independent computations must
  agree and neither of them is the iteration's.

  It is not a default and not a fallback. Requirement 26 keeps the fallback the
  pinned CPU backend, because SPEC-0010 requirement 23 requires a fallback to be
  the implementation the project already treats as authoritative.

  Two departures from the published method are deliberate and made for
  determinism: the step size is fixed rather than line-searched, and the power
  iteration count is fixed rather than convergence-driven. An adaptive step retries
  an input-dependent number of times, and the trial count would then depend on
  rounding. The cost is convergence rate, about which this project claims nothing
  in either direction.

- `optimizer solve --backend highs|host-lp` and `--lp-settings <path>`, under
  SPEC-0011 requirements 18 and 25. The pinned CPU backend stays the default, and
  it is the default in the strongest available sense: no threshold exists anywhere
  that could promote a solve to another backend, so nothing could say otherwise. A
  dispatch threshold is a recorded measurement under requirements 18 and 19 and is
  deliberately not committed here; `state/known-failures.md` records why.

  Settings are required when the first-order backend is named and refused for a
  backend that has none, so a caller who thinks they configured something is told
  they did not rather than having the flag ignored.
- `schemas/lp-settings-v1.schema.json`, and `examples/lp-settings-v1.json` and
  `examples/lp-model-v1.json` alongside it. The settings are their own document
  because a caller passes one on the command line, so it must be checkable on its
  own; a solve record `$ref`s it exactly as it already `$ref`s the solve
  configuration. The new example model is continuous because the existing one is
  discrete, which the first-order backend refuses by design.

- `optimizer-lp-cuda` and the `lp_pdhg` code object: the first-order method's
  kernels running on a device SPEC-0010 selected and leased. A separate crate
  rather than a module inside `optimizer-cuda`, which every existing GPU consumer
  depends on and which would otherwise compile a linear-programming engine none of
  them calls. It inherits the workspace lints, so it forbids unsafe and opens no
  second boundary: it reaches hardware only through `optimizer-cuda-sys`, the one
  ADR-0009 authorizes, which gains an `f64` kernel argument and nothing else.

  The device proposes and the host certifies. Every claim a record carries --
  objective, feasibility, bound, termination -- is produced on the host from the
  original model, so a wrong kernel yields a refused candidate or a weak bound
  rather than a wrong answer.

  Reductions use the same fixed partition and tree the host uses, including the
  second level that reduces per-segment partials. Accumulating those partials left
  to right instead would agree on every line of at most one segment and disagree on
  every wider one, which is why a deliberately wide row is part of the acceptance.
  The kernels are built with `-fmad=false`, which makes device iterates bitwise
  identical to the host engine's; that is a property of this toolchain pair and is
  re-verified by the suite rather than claimed as a contract, since requirement 8
  asks only for same-device reproducibility.
- `tools/check.sh` refuses atomic accumulation in the LP kernels outside the
  deliberately nondeterministic build. It is CPU-only and is the only guard on a
  host with no GPU, where the device suite that would catch it reports a skip.
- `optimizer solve --backend cuda-lp --device GPU-<uuid>`, which runs the
  first-order method on a leased device and falls back to the pinned CPU backend on
  an availability failure, under SPEC-0011 requirement 20 and SPEC-0010
  requirements 24 and 26. The fallback is the pinned adapter and never the host
  first-order method: SPEC-0010 requirement 23 requires a fallback to be the
  implementation the project already treats as authoritative.

  A device that cannot be opened is refused rather than fallen back from, because a
  record must not claim a device the run did not use. A device that opens and then
  cannot do the work is an availability failure and does fall back. Both rules are
  deliberate and they are not the same rule; `state/known-failures.md` records the
  boundary.

### Changed

- **Breaking:** solve records move to `solve-record-v2`, under SPEC-0011
  requirements 9 and 10. The record gains `lp_settings`, carrying the
  preconditioner, the termination check interval and the rest of a first-order
  method's configuration. Both change the iterates, so a record without them would
  not describe the solve it came from. The field is absent for a backend that has
  no such settings, which is what the pinned CPU adapter writes; an empty block
  would claim a preconditioner that was never applied.

  The embedded solve *configuration* stays at version 1, and that is what confines
  the change. A configuration is embedded in `search-config-v3`, so bumping it
  would have moved the search configuration, the search record and the run record
  too -- four documents to record something no configuration carries. Nothing
  embeds a solve record, so it moves alone. `SOLVE_SCHEMA_VERSION` keeps its value
  and now names the configuration only; `SOLVE_RECORD_SCHEMA_VERSION` names the
  record.

  Migration: set a version-1 record's `schema_version` to 2. There is no automatic
  migration and version 1 is refused rather than upgraded, in both the Rust parser
  and the JSON Schema.

- **Breaking:** `Backend` gains a `capabilities` method, under SPEC-0011
  requirements 1, 2 and 4. A backend now states the problem classes it accepts, its
  arithmetic width, whether it takes a warm start and whether it runs on a device,
  so a caller can know what an implementation supports without knowing which
  implementation it holds. `solve` is unchanged, and no schema or wire format moves.

  Migration: an out-of-tree `impl Backend` adds one method returning
  `BackendCapabilities::declare(..)`. The trait had exactly one implementor in this
  workspace and two test doubles, all updated here.

  A declaration's fields are private, which is requirement 4 in the type rather than
  in prose: a caller must not be able to widen one. Privacy alone would only stop a
  local mutation, so `capabilities` also takes no argument, and a backend consults
  its own declaration inside `solve` -- which is what makes a widened copy useless
  to whoever holds it.
- `ProblemClass` now lives in `optimizer-core` beside the solve contract and is
  re-exported from `optimizer-extension`, so every existing path keeps working and
  no document changes. Both a backend declaration and an extension declaration need
  the concept, and two enums with the same variants and the same wire form would let
  a registry entry's `continuous` and a backend's `continuous` drift into unrelated
  facts.

- A registry entry requiring a GPU now resolves when the run holds a device, and is
  still refused when it does not, under SPEC-0010 requirement 35. This narrows
  SPEC-0009 requirement 9's unconditional refusal rather than removing it, and
  requirement 14a is unaffected: the decision is still made from the entry and the
  context, before the provider is consulted and with nothing constructed.
- A configuration naming a device but registering no extension that needs one is
  refused. Requirement 6 has two halves and they live in two places: the executive
  refuses a device with no registrations at all, which is all it can see, and the
  run surface refuses a device no registered entry requires, because the hardware
  requirement lives in the registry it resolved. Running anyway would record a
  device that sat idle and verification would agree with it.
- **Breaking:** search configurations, search records and run records move to
  `search-config-v3`, `search-record-v3` and `run-record-v2`, under SPEC-0010
  requirements 40 and 41. The configuration gains one field, `device`, which is
  `"cpu"` or a physical GPU UUID; the other two move only because a search record
  embeds its configuration and a run record embeds that search record. Earlier
  versions are refused rather than migrated, in both the Rust parsers and the JSON
  Schemas, which are asserted to refuse the same documents.

  The device is in the configuration rather than in provenance, and that is what
  costs the cascade. Provenance would have moved no versions at all -- and would
  have put the device somewhere `optimizer verify` never reads, because
  verification re-runs a search from the embedded configuration alone. A device
  recorded only in provenance would describe a run the run surface could not repeat.

  Migration: add `"device": "cpu"` to a version-2 configuration and set
  `schema_version` to 3. There is deliberately no automatic migration: a version-2
  record of a device run and a version-2 record of a CPU run are the same bytes, so
  defaulting an absent device would have to invent the fact that distinguishes them.

  One value governs a whole search rather than one per component, because SPEC-0006
  requirement 6 permits one lease holder across device selections -- a search cannot
  use two devices, so a per-component field could express what the lease forbids.
  The solve configuration is therefore unchanged at version 1 and a relaxation
  inherits the search's device.
- A search configuration naming a GPU is **refused** as unsupported rather than run
  on the CPU. No search path dispatches to a device yet, and running one anyway
  would be worse than an error: the record would name the device it was asked for,
  verification would re-run it on the CPU and agree, and that agreement would
  certify a hardware claim nothing checked.
- `neh` and `insertion` score insertion positions from head and tail completion-time
  arrays instead of rebuilding and re-evaluating each trial sequence, which is
  Taillard's exact acceleration and reduces a pass from `O(n^3 m)` to `O(n^2 m)`. The
  arithmetic is the recurrence's own and lives in `evaluate`, so requirement 8's rule
  that nothing proposing a schedule owns a second definition of what one costs is
  preserved. Behavior is unchanged, and that is asserted rather than argued: a
  contract test compares both heuristics against the pre-change algorithm over the
  fixed grid and all ten frozen Taillard instances and requires the *same
  permutation*, not merely the same makespan, because requirement 17 fixes which of
  several tied permutations a caller receives.

  Measured on the development host, release build, best of three after a warmup,
  over the whole scale split: the improvement pass on `ta081` (100x20) falls from
  32.49 ms to 0.92 ms and on `ta101` (200x20) from 257.39 ms to 3.75 ms, a speedup
  growing from roughly 4x at twenty jobs to roughly 69x at two hundred. The ratio
  tracks the job count rather than the machine count, which is what an `O(n)` factor
  should do. This is a development diagnostic on one host and is not a benchmark
  result, not evidence, and not a claim about the engine.

### Added

- Device work is launched in bounded chunks with a cancellation check between them,
  under SPEC-0010 requirement 27, so a cancelled run waits for one chunk rather than
  for a whole batch. The chunks bound *work* rather than calls: 4,096 permutations
  for the batch kernel and 128 removed jobs for the neighbourhood kernel, which at
  the largest supported shape are 4.1e7 and 2.6e6 integer operations respectively.
  `makespans` and `insertion_neighborhood` therefore take a `CancellationToken`.
- A sticky device fault poisons its residency, which then refuses without touching
  the device. Requirement 29 allows rebuilding the context or falling back for the
  rest of the run; this takes the second, so one fault does not become a stream of
  them with the first buried.
- `GpuSchedulingProducer` falls back to the host when the device declines, and the
  fallback is `optimizer_schedule::insertion_neighborhood` -- the CPU path this
  project already treats as authoritative, not a second implementation written to
  match the kernel, so the two cannot drift. A caller cannot tell which ran, which
  is the point; the producer's `fallbacks()` counter is how a test can.
- `flow-shop-neh-gpu`, the first candidate producer whose work runs on a device,
  under SPEC-0010 requirements 26 and 33 to 35. Construction stays on the CPU --
  NEH is `O(n^2 m)` and the measured crossover puts a device behind the CPU below
  roughly fifty jobs -- and the device evaluates the full insertion neighbourhood,
  which is the batched part and the part the crossover measured.

  It holds no more authority than any other producer. Its proposals are complete
  permutations that `Model::evaluate` validates against the original model, so a
  wrong kernel produces a recorded refusal rather than a wrong incumbent; that is a
  property of the seam it reaches the engine through, not of the producer's good
  behaviour.
- `DeviceSession`, one leased open device for the duration of a run. Holding one
  means, by construction, that the host lease was taken and a context was created on
  the named device and its identity was read back from the driver; the lease is
  released after the context is destroyed. A run naming a device that cannot be
  opened is refused rather than falling back, because the caller asked for that
  device and a silent CPU run would record hardware it never touched.
- A run record's `hardware` block now names the device when one was held, which
  gives SPEC-0007 requirement 9 its producer. The three GPU fields are all null or
  all populated, and they come from a `DeviceSession` rather than a configuration
  string, so a record cannot name a device the run did not open.
- `optimizer gpu probe --device GPU-<uuid> [--lease acquire|inherited]
  [--timeout-ms N]`, under SPEC-0010 requirements 3, 4 and 9. It takes the shared
  host lease, creates a context on one named device, and writes one JSON report; a
  refusal exits 2 and writes nothing, so a partial report can never be read as a
  successful one. It names exactly one UUID because the lock permits one holder
  across device selections, so a probe-everything form would be a command the lease
  forbids.

  The report keeps `requested` and `observed` as separate fields. Equality of the
  two is the check requirement 3 makes, and one field would record the answer
  without recording that anything was compared. It also reports the compute
  capability, multiprocessor count, the shared memory a block may address, free and
  total memory, and which kernels the provisioned code object actually provides --
  resolving each entry point without launching any of it, so a build mismatch is
  found by a probe rather than by a first launch.

  Under `tools/gpu_job.sh` the lease is inherited. `--lease acquire` inside a
  wrapped job waits on the lock its own parent holds and refuses at the timeout,
  which is the deadlock the inherited form exists to prevent, now bounded and
  visible rather than a 300-second hang.
- Discovery reports the driver version, SPEC-0006 requirement 1a. SPEC-0007
  requirement 9 has required a GPU record to identify its driver since M0 and
  nothing produced the field until now. A row without one is refused rather than
  accepted with a hole, so the producer cannot sometimes produce nothing. Note that
  `Hardware::driver` in a run record is still null and correctly so: every search
  this build performs is a CPU search, and requirement 9 forbids a CPU record
  claiming GPU execution.
- The CUDA driver boundary, under SPEC-0010 and ADR-0009. `optimizer-cuda-sys` is the
  workspace's second and last unsafe crate; it resolves `libcuda.so.1` with `dlopen`
  rather than linking it, so an ordinary `cargo build` still works on a host with no
  CUDA toolkit and no device, an absent driver is a typed error rather than a link
  failure, and no NVIDIA code is linked or redistributed. No third-party crate was
  added: `libc` was already in the lockfile. `optimizer-cuda` keeps
  `unsafe_code = "forbid"` and keeps discovery, the lease and residency.
- Two device kernels for batched flow-shop evaluation, compiled out of tracked source
  by `tools/setup_cuda.sh`. `nvcc` is a provisioning dependency, never a build
  dependency. Both are pure 32-bit integer: at compute capability 12.0 that runs at
  the full lane rate, and it makes CPU/GPU agreement an exact identity rather than a
  tolerance. The head and tail tables are 32-bit because 64-bit ones would need
  160,000 bytes at the largest supported instance, where a block may address 99 KB.
- `ScheduleResidency`, which uploads an instance once and reuses it across calls, and
  refuses a device before any allocation when the instance's own makespan bound
  exceeds the kernel's range, when the shape needs more shared memory than the device
  allows, or when the compute capability is older than the code object.
- `Ownership::acquire_or_inherit`, which accepts a lease an ancestor already holds.
  `tools/gpu_job.sh` takes the lock and execs its child, so a child that acquired
  again would block on itself until the wrapper's 300-second timeout.
- `optimizer_schedule::insertion_neighborhood`, the whole insertion neighborhood of
  one permutation scored from a single starting point. Unlike `insertion`, which is
  sequential because an accepted move is visible to the next job, this scores the
  jobs independently, which is what makes it expressible as a batch and therefore
  what a device can compute. It is also the CPU path the device must agree with.
- Device acceptance tests, opt-in behind `AI_OPTIMIZER_GPU=1` so the ordinary gate
  stays CPU-only and no task record's "CPU only" resource budget is made false. They
  assert equality against the host recurrence at tolerance exactly zero, agreement
  with a full recomputation, bitwise-identical repeats, one upload per residency, and
  that a nonexistent UUID and an absent code object are each refused by name.
- `tools/gpu_check.sh`, device acceptance plus `compute-sanitizer` with memcheck,
  racecheck, initcheck and synccheck. It refuses to run without an inherited lease
  rather than taking one, so it cannot be invoked outside the wrapper that names a
  single device, and it warns loudly rather than passing silently when
  `compute-sanitizer` is absent. All four are clean on an RTX 5090.
- A first crossover measurement, recorded in
  [known failures](state/known-failures.md). The device loses at 20 jobs by a factor
  of four, crosses over at roughly 50, peaks at 16x on 200x20 and falls back to 9.5x
  at 500x20; context creation costs about 148 ms and dwarfs every other number. It is
  a development diagnostic on one host, not a benchmark result and not evidence, and
  no default consults it yet.
- A frozen Taillard scale split, under ADR-0011, at
  `benchmarks/manifests/taillard-flow-shop-scale-v1.json`. It takes the first
  instance of each of the paper's twelve published classes, spanning 20 to 500 jobs
  and 5 to 20 machines, and exists to locate a crossover rather than to sample one
  shape. The development subset is unchanged: its ten instances, its shape and its
  seeds are untouched, so every C5 claim that cites it still holds. Instances are
  generated from the published seeds by the committed generator and checked by
  regenerating them with an independently written one, so the split needs no
  download and no third-party host. It commits no best-known bound, because a
  committed bound is an acceptance threshold.
- `SCALE_SUBSET`, the published seed table behind that split. Taillard reuses seeds
  across classes — `ta051` and `ta071` share one — so a seed is unique only together
  with its shape, and the contracts assert that pair rather than the seed alone.

- `Model::rebound`, which replaces a model's variable domains and bounds while
  reusing its already-validated rows and objective, under new SPEC-0001
  requirement 2a. It is the relaxation path branch-and-bound builds one subproblem
  per node with, not a general-purpose constructor: it refuses any variable list
  that does not name exactly the original variable IDs, and that refusal is what
  makes skipping the row checks sound rather than merely cheaper.
- C8 local extension registry and conformance, under SPEC-0009 and ADR-0008. A
  registry document maps a declared extension identity to an extension this build
  provides, together with the facts needed to decide whether to permit it: version,
  license, category, authority basis, host contract compatibility, declared
  determinism, counted limits, data and hardware needs, inter-extension
  requirements and conflicts, and promotion state. Before this, the extension
  runtime was reachable only from Rust test code.
- `optimizer search`, `optimizer verify` and `optimizer schedule solve` accept
  `--registry` and resolve a configuration's extension policy through it. This
  closes the gap C5 recorded: a scheduling run performed with the NEH producer is
  now verifiable by re-execution, where before it was refused as unsupported.
- `optimizer registry list` reports every entry a registry records, and separately
  whether this build provides the identity at all, so an entry that would be
  refused is visible without attempting a search. `optimizer registry check` runs
  the conformance suite over one entry and writes its record.
- The registry resolves; it does not load. An entry names an extension the binary
  already provides through a caller-owned provider seam, and an entry naming an
  identity this build does not provide is refused rather than skipped. Dynamic
  loading of separately distributed native components stays deferred with its
  recorded blocker: it needs an unsafe boundary, an ABI stability contract, a
  lifecycle and unload story and crash-isolation evidence. ADR-0009 has since
  authorized one unsafe boundary, for CUDA and no other, so the blocker is narrower
  than it was when this was written but is not removed.
- Resolution is total: it either produces a resolved set for every named entry or
  refuses, so a search never begins with a subset of what it was configured with.
  The extension's own declaration is authoritative and an entry is a claim about
  it; a disagreement on version, category, host contract version, problem class,
  determinism or limits is refused in both directions rather than reconciled.
- Promotion is checkable rather than assertable. A promoted entry cites a
  conformance record by path and SHA-256, and is refused when the record is absent,
  its bytes do not match, its outcome is not a pass, or it names another extension
  or version. An experimental entry needs `--allow-experimental`, and a record
  written with one registered carries a warning naming it.
- A conformance record and a registry document are new versioned strict-JSON
  documents at `schema_version` 1, each with a JSON Schema that accepts exactly
  what the Rust parser accepts. No existing schema version changed and no existing
  document gained or lost a field, so the committed C4 example record still
  verifies unchanged.
- Nothing here grants an extension mathematical authority. Resolution decides which
  extensions a search may consult; SPEC-0004 continues to decide what their output
  is worth. Promotion means the contract conformance suite passed, never that the
  extension improves a search, and no performance or solution-quality claim is made
  or measured.
- C5 flow-shop scheduling slice, under SPEC-0008 and ADR-0007. This is the first
  application workload with an independent notion of a correct answer: a makespan
  recurrence computes a schedule's cost from a job order, so a candidate is checked
  against a definition rather than against another solver.
- `optimizer schedule generate` writes a flow-shop instance from a published
  Taillard seed, and `optimizer schedule solve` encodes an instance, registers the
  NEH producer, runs the executive and writes a SPEC-0005 run record. `solve` also
  writes the encoded model, which is what a caller hands `optimizer verify`: a run
  record's fingerprint is computed from the model that was searched, and for a
  scheduling run that is the encoded model rather than the instance.
- Flow-shop instances are versioned strict-JSON documents. A ragged matrix, a
  processing time that is zero or negative, a matrix disagreeing with its declared
  shape, an unknown or duplicate field, and a positional array are each refused at
  parse time rather than clamped or repaired.
- The positional encoding turns an instance into an ordinary model with no big-M
  constant, so the existing solve, search, extension and run-record contracts apply
  unchanged: no new record type, and no schema version changed anywhere.
- Deterministic NEH and insertion candidate producers, registered by a caller and
  never loaded by default. They hold no authority: every proposal is validated
  against the original model and the recorded objective is that recomputation.
- A frozen Taillard development subset, the published 20x5 class, generated from
  the seeds in the cited paper rather than downloaded. The manifest records each
  instance's generator, seed and parameters beside its checksum, so the derivation
  is verifiable and the gate needs no network access.
- C5 acceptance evidence: the proven optimum on encoded models equals exhaustive
  enumeration of every permutation over a fixed grid; the generator reproduces
  Taillard's published `ta001` matrix exactly; a producer whose proposals are all
  refused leaves the outcome, proven optimum, dual bound, forfeiture state and both
  prune counters identical to the producer-free run; and a scheduling run record
  verifies by re-execution.
- No performance or solution-quality claim is made. The positional encoding's
  linear relaxation is weak, so proven optimality is asserted only for tiny
  instances, and no best-known bound is committed as a threshold.

### Fixed

- CI reuses the verified pinned cargo-deny 0.19.0 binary restored from cache;
  missing or mismatched binaries are replaced with the same locked version.
  This avoids an installation failure when Cargo metadata was not cached.
- GPUP-1 repairs host LP certification used by both `host-lp` and `cuda-lp`.
  Products, fixed-tree sums, reduced costs, variable contributions, and the final
  bound now carry outward binary64 enclosures. A reduced cost rounded to zero
  retains uncertainty; an infinite variable side or nonfinite arithmetic that
  prevents certification yields no bound. The original cancellation reproducer
  previously returned an invalid zero lower bound.
- Both first-order backends share a conservative, objective-sense-aware gap check.
  It encloses the original objective including its offset, fixes maximization gap
  direction, and prevents objective cancellation or overflowing tolerance arithmetic
  from producing an optimality claim. LP record gaps remain absolute objective-unit
  diagnostics, now nonnegative upper enclosures; the reported objective and caller
  feasibility tolerances retain their existing meanings. Bounds can be weaker or
  absent when uncertainty prevents a finite certificate.
- Independent rational fixtures cover 1,083 primitive cases, five reductions,
  26 certification cases, and 18 gap cases, with native host and leased-device
  maximization integration tests. See
  [LP certification arithmetic](docs/architecture/lp-certification.md).

- The branch-and-bound node path no longer performs work it discards. The backend
  extracted an LP basis on every node — computing the model's canonical
  fingerprint, which serializes the whole model — for a value `Backend::solve`
  dropped immediately and that SPEC-0003 requirement 23 forbids reusing across
  nodes. Evaluation and structural diagnostics were formatted eagerly, costing
  several string allocations per matrix nonzero on the success path for text a
  valid model never produces. Both are now built only when a check fails.
  `Candidate::canonical` cloned and re-sorted a candidate the backend had just
  built by iterating the model's own sorted variables, and now borrows when the
  input is already canonical. `node::relaxation` rebuilt each subproblem through
  `Model::new`, revalidating every row and the objective once per node for data
  the node did not touch, and now uses `Model::rebound`, which validates the
  supplied bounds and refuses any variable list that is not the original's IDs.
  Conclusions are unchanged: every field verification compares, every node
  counter and every diagnostic message is identical, and the messages are pinned
  byte-exactly by tests written against the previous code. No performance
  property is claimed of the engine; `tools/benchmark_search.py` is a development
  diagnostic that records no threshold.

- `tools/verify_committed_record.py` now re-executes a record whose search
  branched. Both committed records reported `nodes_explored: 1`, so the only check
  that re-runs a record against a later build had never descended past the root
  node — the exact blind spot that matters for work on the per-node path. The new
  fixture explores 37 nodes, prunes 23 by bound and proves optimality, and its
  counters are asserted against the committed record so the check cannot decay
  into a third single-node case.

- A run record's identifier no longer depends on measured elapsed time. `optimizer
  search` built `record_id` as `run-{model_id}-{elapsed_ms}` and `optimizer
  schedule solve` built `schedule-{model_id}-{elapsed_ms}`, so a record's identity
  was a property of how busy the host happened to be: two runs of the same search
  got different identifiers, and two unrelated searches that took equally long got
  the same one. Both now derive it from the SHA-256 digests of the input documents
  the record already carries. SPEC-0005 requirement 1a states the rule, so the
  derivation is specified rather than incidental. `record_id` is not among the
  fields verification compares, so no record version changed and existing records
  remain valid.

- `optimizer verify` now refuses a record whose configuration names an extension
  policy, reporting it as unsupported instead of as a divergence. Re-execution
  loads no extension, so such a record was reproduced by a search it does not
  describe and its node counters differed for that reason alone; calling that a
  divergence blamed the record for a limitation of the verifier. SPEC-0005
  requirement 14 already refused such a configuration on the search path, and this
  applies the same rule to verification.

- C4 agent-independent run surface, under SPEC-0005 and ADR-0006. `optimizer
  search` runs the owned executive over the pinned backend and writes a run
  record; `optimizer verify` re-runs that search from the record alone and fails
  on disagreement. Before this, the C2 executive and the C3 extension host were
  reachable only from Rust test code.
- Reproducibility is established by re-execution rather than asserted.
  Verification reads only the configuration embedded in a record, never its
  recorded outcome, objective, bound or counters, so it cannot confirm its own
  input. Divergence in the outcome, recomputed objective, dual bound, gap,
  forfeiture state or any of the five counters is reported by name.
- Measured elapsed time is recorded and excluded from agreement. It describes the
  host rather than the search, so including it would make every verification
  fail.
- A record is bound to model bytes by `Model::fingerprint`, not by `model_id`, so
  a model edited under an unchanged identifier is refused before any search runs.
  This is the rule C1 already applied to LP bases.
- `RunRecord` in optimizer-experiment at schema version 1, carrying source
  revision, dirty state, hardware, toolchain, the canonical model fingerprint,
  the SHA-256 of each input document, and the complete `SearchRecord` embedded
  verbatim. Provenance field names are taken from SPEC-0007's experiment result
  so the repository's two provenance shapes cannot drift apart.
- A search that reached a limit or was interrupted still writes its record and
  reports exit 1 or 130. Only a run that could not start writes nothing, because
  there was no run to describe.
- A configuration naming an extension policy is refused as unsupported rather
  than run without the extension it names, which would record a search the caller
  did not request. That refusal marks the seam the deferred registry fills.
- JSON Schemas for the run record, the search record and search configuration,
  giving C2 and C3 documents their first schema coverage. The Rust parsers and the
  schemas accept the same documents, and nested versions are validated on the
  parse path so neither authority is laxer than the other.
- SHA-256 in safe Rust, checked against the FIPS 180-4 vectors and independently
  against Python's `hashlib` over the committed documents, rather than adding six
  transitive dependencies under a `multiple-versions = "deny"` policy.
- A divergence reports whether the backend library, source revision or compiler
  differs from the one the record names, so a changed engine is distinguishable
  from a wrong result. This is diagnostic only: the ten compared fields are
  unchanged, a record from another build still verifies when its search agrees,
  and a divergence still fails. Whether such a mismatch should ever be tolerated
  is unresolved and needs its own record version and decision record.
- The acceptance gate re-executes the committed example run record against the
  current build. Every other verification test produces its record moments
  earlier in the same process, so none of them covered the property actually
  claimed, that a record outlives its author.
- Fixed: a build that linked no native library recorded `backend_version:
  "1.11.0"` for a pre-cancelled solve, making its record indistinguishable from
  one produced against the real library. It now records the adapter's own report,
  `unavailable`, so provenance cannot claim a library that was never called.
- C4 acceptance evidence: verification is shown to fail as well as pass. A
  perturbed model is refused on its fingerprint, and a mutated outcome,
  objective, forfeiture flag and each counter are detected individually, so no
  field is nominally compared and actually ignored. Agreement establishes
  determinism on one host, not correctness and not optimality; a forfeited search
  stays forfeited after it verifies. Cross-host reproducibility is untested and
  no performance claim is made. The Python SDK, the local registry, checkpoint
  restart and comparative experiment execution are deferred with recorded
  blockers.

- C3 extension runtime and authority model in optimizer-extension, under
  SPEC-0004 and ADR-0005. Extensions declare identity, category, host contract
  version, determinism and counted budgets; the core derives their authority
  from the category and decides what is true. Candidate producers and search
  advisers are the admitted categories.
- Every proposed candidate is validated by `Model::evaluate` against the
  original model before it can become an incumbent, and the recorded objective
  is that recomputation. An objective an extension asserts is never read.
- No extension path can forfeit a proof claim, end a search or return an error.
  An adversarial extension can waste its budget and have everything refused; it
  cannot deny a proof the engine would otherwise complete.
- Advised branching is restricted to variables the executive itself found above
  its integrality tolerance at that node. Branching on an integral value would
  produce two children that do not tighten the node, so the search could
  regenerate an identical child forever.
- Typed extension failures in search records: invalid candidates, invalid
  advice, both directions of contract-version mismatch, a refused
  transformation category, an unclaimed problem class, contained panics and
  exhausted budgets. Counters stay exact while retained messages are capped, so
  an extension refused once per node cannot grow a record with the search.
- Search configuration, search records and checkpoints move to schema version 2.
  Configuration carries the caller's extension policy and records carry one
  summary per permitted extension, so a record cannot conceal that extensions
  influenced it. Version-1 documents are rejected rather than migrated.
- `search_with_extensions` alongside `search`, which remains the extension-free
  entry point. A search with an empty policy produces the same record as the
  extension-free one apart from measured elapsed time.
- optimizer-extension-examples: three honest extensions and three hostile ones
  covering 17 distinct misbehavior modes, depending only on the published
  extension and core APIs with the executive as a test-only dependency. That
  they build and run is the evidence that a third-party extension needs no
  engine-internal change.
- C3 acceptance evidence: over a fixed model grid every hostile extension leaves
  the outcome, proven optimum, dual bound, forfeiture state and both prune
  counters identical to the extension-free run, which itself agrees with
  brute-force enumeration. Extension containment covers panics, not a process
  abort. No performance claim is made.

- C2 owned branch-and-bound executive in optimizer-solver, under SPEC-0003 and
  ADR-0004. It owns node state, budgets, cancellation, incumbent acceptance and
  proof completion, and consumes the C1 backend contract purely as a relaxation
  service without depending on any particular backend.
- `SearchOutcome`, a proof claim distinct from the backend's `Termination`:
  proven optimality means the executive exhausted its own node tree, not that
  one relaxation solve reported optimality.
- A relaxation objective is admitted as a dual bound only when that relaxation
  proved optimality. Any limit, interruption or failure leaves the node bound
  unavailable, forbids pruning that node, and permanently forfeits the search's
  proof claim, recorded as `forfeited` so a reader can see why a completed-looking
  search claimed nothing.
- Versioned search configuration, search record and checkpoint documents at
  schema version 1, with absent measurements omitted rather than serialized as
  null. The checkpoint shape is defined and serializable; restart is deliberately
  not implemented and needs its own acceptance evidence.
- C2 acceptance evidence: 192 tiny discrete models agree with brute-force
  enumeration of the entire assignment space on both proven optimum and proven
  infeasibility, plus end-to-end agreement with independent subset enumeration
  over the pinned HiGHS relaxation service. No performance claim is made.

- C1 backend-neutral solve contract: explicit solve options with no default
  seed, limits or tolerances; cooperative cancellation; engine-owned termination
  that never reports a limit, interruption or failure as proven optimality;
  model-bound candidate and LP-basis warm starts; and reproducible solve records
  in which an absent measurement is omitted rather than serialized as null.
- Pinned CPU HiGHS 1.11.0 LP/MILP backend behind a private FFI boundary, with
  every native model status mapped explicitly, native handles destroyed exactly
  once, and every extracted candidate re-validated against the original model
  before publication.
- `optimizer solve --model PATH --config PATH [--candidate PATH | --basis PATH]`,
  with exit 0 for a completed outcome, 1 for a limit, 130 for interruption and 2
  for argument, I/O, unsupported, backend or numerical errors.
- Versioned solve configuration and solve record JSON Schemas, plus their
  negative acceptance tests.
- `tools/setup_highs.sh` is now part of the acceptance gate. Running without the
  native library requires `AI_OPTIMIZER_SKIP_NATIVE=1` and is reported as
  uncovered native acceptance rather than a full pass.

### Changed

- Replaced the narrow M0-M6 implementation sequence with an evidence-staged
  roadmap covering the completed contract stage and the planned execution,
  application, research, hardening and reproduction stages.
- Solve errors use the existing `ErrorKind` taxonomy, extended with
  `unsupported` and `backend` categories, instead of unstructured strings.
- `optimizer-highs` declares its own lints rather than inheriting the workspace
  set, because a workspace-level `unsafe_code = "forbid"` cannot be relaxed by an
  inner crate; every other runtime crate keeps the prohibition.
- The acceptance gate runs cheap preconditions before compilation and falls back
  to the cached RustSec database when the advisory fetch is unavailable.

### Fixed

- Record parsing validates the versions of the documents nested inside a
  record, not only the record's own version. The version-1 JSON Schemas already
  pin every nested `schema_version`, so `SolveRecord::from_json`,
  `SearchRecord::from_json` and `Checkpoint::from_json` previously accepted
  documents `tools/validate_artifacts.py` rejects. A wrongly versioned
  incumbent, validation report, relaxation configuration, extension summary or
  extension policy is now a document error at parse time. Strictly narrowing:
  no document that was valid under both paths becomes invalid.

- Model and candidate file paths preserve native OS strings, including non-UTF-8
  Unix names; malformed command/flag/tolerance text returns an argument error.
- Incomplete and unknown model commands include the argument error category.
- Model and candidate JSON now reject positional records and object-wrapped
  domain/objective enums, including direct Serde parsing and nested records.
- Model validation report write and flush failures return a categorized I/O
  diagnostic and exit code 2, including full output devices and closed pipes.
- Candidate domain evaluation no longer relies on an unreachable branch, so
  adding a variable domain cannot introduce a latent panic.

### Added

- M1 original linear models with stable IDs, explicit bounds and continuous,
  integer and binary domains, immutable structural validation and canonical JSON.
- Original candidate objective, bounds, row and domain checks with explicit
  tolerances, inspectable violations/allowances and checked numerical failures.
- CPU model/candidate validation CLI, versioned examples, independent exhaustive
  tests, file-size boundaries and strict JSON regression coverage.

- M0 Rust workspace with a pinned toolchain and seven ownership boundaries.
- Bootstrap CLI, JSON GPU discovery, and cancellable simulated exclusive leases.
- Versioned configuration, manifest, and result schemas with provenance checks.
- CPU CI, documentation builds, dependency policy, and manual serialized GPU CI.
- Contract tests, bounded smoke artifacts, project rules, and milestone backlog.

No CUDA kernels, Python SDK, extension registry, dynamically loaded native
extensions, or solver performance claims are included. Owned branch-and-bound
search proves optimality but is not tuned and is not compared against any other
solver. Extensions may propose candidates and search actions; the core validates
every one, and extension containment covers panics rather than a process abort.
Relaxations are single-threaded CPU HiGHS under recorded numerical settings; no
benchmark comparison is claimed.
