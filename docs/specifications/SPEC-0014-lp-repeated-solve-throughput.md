# SPEC-0014: Repeated-Solve LP Throughput with Explicit Matrix, Context and Device Reuse

Status: accepted by the maintainer's implementation request, 2026-09-20
Scope: opt-in repeated-solve sessions for cuda-lp-tuned and the isolated research
executable
Owner: numerical backend and experiment tooling
Introduced: GPUP-THROUGHPUT
Last reviewed commit: pending
Supersedes: none; extends SPEC-0010, SPEC-0011, SPEC-0012 and SPEC-0013
Implementation: pending
Tests: pending

## Purpose

The GPUP-5C report showed the remaining LP solve cost is outside arithmetic: context
creation is 208-330 ms of a 400-600 ms certified solve at study size, and at 65536 rows
preconditioning (about 940 ms) and research preparation (about 1020 ms) each exceed the
19-30 ms of total kernel time in a 200-proposal run. Nothing in the project amortizes
any of it: every solve is one fresh process that creates a context, reads and hashes the
code object, builds the LinearProgram and Engine (plus the research Operator), opens an
LpResidency, solves, and drops everything.

This specification defines an opt-in repeated-solve session that pays those setup costs
once for a batch of solves over one fixed matrix, and an amortized-throughput endpoint
that reports the result. It exists to produce setup-cost evidence and a bounded,
clearly labeled throughput measurement — not to change how any existing solve runs.

Explicit exclusions: no warm starts or iterate carry-over between solves; no objective,
row-bound or matrix changes within a batch; no multi-context or multi-device use; no
threads; no presets or dispatch; no change to `Backend::solve`, backend selectors,
defaults, existing schemas' meanings, or any archived evidence; no promotion of
amortized numbers into the single-solve latency endpoint.

## Terminology

- Session: one open device context and resident matrix, opened explicitly, solved
  against repeatedly, and closed explicitly. A session is bound to one device, one code
  object, one matrix, one objective, one set of row bounds and one settings document.
- Prepared matrix: the host-side, matrix-only solve state — the preconditioner, the
  scaled matrix in both orientations, the scaled objective and the spectral step. The
  research path adds its Operator, which reads only the matrix, preconditioner and step.
- Resident matrix: the device buffers uploaded once at session open (matrix in both
  orientations, objective, row bounds, column bounds of the base model).
- Batch: an ordered sequence of N solves in one session, described by one
  lp-batch-request-v1 document.
- Solve: one independent PDHG run within a batch, from a cold iterate to its own
  termination, with its own diagnostics, counters, certification and record.
- Repeat: a batch kind whose solves all use the base model unchanged.
- Variant: a batch kind whose solve k uses a materialized variant model that differs
  from the base model only in variable bounds, generated by the variant contract below.
- Materialized variant model: the complete Model bytes produced by the deterministic
  materialization function; it, not a description of the change, is what is solved and
  hashed.
- Setup cost: the one-time phases of a session — device context, module load,
  preconditioning, research preparation, invariant allocation and upload.
- Per-solve cost: the phases repeated for each solve — variant rebind, engine rebind,
  bound upload when bounds changed, and the endpoint phases of the solve itself.
- Fresh-process single-solve endpoint: the primary endpoint of SPEC-0013 requirements
  10-13 — a monotonic clock around a fresh-process single solve, process launch through
  validated output. Unchanged by this specification.
- Amortized per-solve time: batch elapsed time divided by N, and its reciprocal
  throughput in solves per second. A separate, separately labeled endpoint.

## Requirements

### Authority and endpoints

1. The fresh-process single-solve endpoint MUST remain the primary endpoint and MUST be
   unchanged: `optimizer solve` behavior, records, defaults and schemas keep their
   existing meanings and bytes for any input.
2. Amortized repeated-solve throughput MUST be reported only as its own labeled
   endpoint — amortized per-solve time (batch elapsed / N) and solves per second. It
   MUST NOT be substituted for, tabulated as, or merged into one latency table with
   fresh single-solve latency; any report comparing the two MUST title the comparison
   as separate endpoints.
3. Warm-resident and kernel-only timings MUST be labeled secondary diagnostics, as
   SPEC-0013 requirement 13 already requires.
4. Every surface this specification adds MUST be opt-in: explicit session API calls,
   the `optimizer solve-batch` CLI command, and the research executable's
   `batch`/`verify-batch` actions. No selector, dispatch rule, default or preset may
   route a solve through a session.
5. Every solve in a batch MUST run `Model::evaluate` on the materialized model actually
   solved, plus host-side `certify` and `assess_gap`, exactly as the single-solve path
   does. A device never holds mathematical authority (ADR-0010); batching changes no
   certification arithmetic.

### Reuse boundaries

6. A session MUST fix exactly one device context, one code object (read and hashed once
   at open), one constraint matrix, one objective, one set of row bounds and one
   settings document for its lifetime.
7. Reusable host state MUST be exactly: the preconditioner, the scaled matrix in both
   orientations, the scaled objective, the spectral step, and on the research path the
   Operator. Nothing derived from variable bounds may be reused across a variant
   boundary.
8. Each solve in a batch MUST start from a fresh controller and the cold iterate; no
   primal, dual or anchor state may carry over between solves.
9. Each solve MUST produce a fresh LpDiagnostics and fresh execution counters;
   batch-level aggregates MUST live only in the batch record, never in the per-solve
   endpoint records.
10. Executor upload gating and research guard slots MUST be reset per solve — by a
    fresh executor or an explicit per-solve reset that zeroes the guard slots as a
    counted upload — so a reused executor can never silently keep a previous solve's
    terminal iterate or guard state.
11. A variant MUST differ from the base model only in variable bounds. The session MUST
    refuse a variant whose matrix, objective, row bounds or variable ID set differ from
    the session's, and the refusal MUST happen before any allocation or upload for that
    solve.
12. Before a variant solve, only the column-bound buffers may be re-uploaded
    (SPEC-0010 requirements 16 and 18). A repeat solve MUST upload only per-solve
    working state. Bound re-uploads MUST be counted separately from the one-time
    invariant upload: the residency's `uploads()` stays 1 for the session and a
    separate `bound_rebinds` counter records rebinds.
13. Memory admission MUST be performed once at session open. A device fault poisons the
    session; subsequent solves MUST be recorded not_attempted with the fault as reason
    (SPEC-0010 requirement 29), and records for earlier completed solves MUST be
    retained.
14. Cancellation MUST be observed between solves and at the existing chunk boundaries
    within a solve; records for solves completed before cancellation MUST be retained.

### Bitwise identity

15. Each batch solve MUST produce primal and dual bits, logical iteration and restart
    counts, termination status and launch count identical to a fresh-process single
    solve of the same materialized model, settings, code-object bytes and device.
16. Variant materialization MUST be one deterministic pure function of (base model,
    batch request, solve index); the materialized model bytes and their SHA-256 MUST be
    recorded per solve in the batch record and in the per-solve record's request hash.
17. Bitwise identity MUST be verifiable from the retained evidence alone — by
    re-materializing variants and re-verifying each per-solve record — and MUST be
    reported as counts (identical out of compared), not asserted.

### Variant contract

18. Variants MUST tighten bounds toward the instance's frozen witness: each changed
    bound moves toward the witness value, brackets it, and stays strictly inside the
    original bounds, so the witness remains feasible for every variant.
19. The generator MUST use the SHA-256 counter PRNG of the instance generator with a
    recorded seed band (the protocol's variant seed base plus the instance's index),
    MUST change exactly min(n, 256) variables, and MUST express bound movements in
    dyadic fractions so variant bounds are exact in both FP64 and FP32.
20. Variant k MUST be identical across batch sizes: the variants of a size-N batch are
    the first N of any larger batch of the same instance and seed (prefix property).
21. A variant batch MUST be refused for an instance without a frozen witness.

### Evidence

22. lp-batch-request-v1 MUST record: schema_version, kind (repeat or variant), the
    number of solves, the variant list (index plus changed variable bounds), the
    generator seed, and the batch time limit.
23. Batch evidence MUST be a directory containing one batch record plus one record per
    solve; each per-solve record MUST be an individually verifiable lp-endpoint-v3
    (CLI) or research-v2 (research executable) document whose existing meaning is
    unchanged.
24. The batch record MUST separate setup phases (device_context, module_load,
    preconditioning, research_preparation, invariant_allocation_upload) from per-solve
    session phases (variant_rebind, engine_rebind, bound_upload) and from the per-solve
    endpoint phases. These batch phase names MUST NOT be added to the lp-endpoint phase
    allow-list; endpoint records keep their existing phase vocabulary.
25. Per-solve files MUST be written with create_new into a temporary name and renamed
    into place; every file MUST fit the supervisor's per-file limit (32 MiB), so one
    solve's evidence never embeds the model or another solve's record.
26. The batch record's payload hash MUST bind the request hash, the base model hash and
    every per-solve record hash and status, in solve order.
27. A solve that is not attempted (poisoned session, cancellation) MUST be recorded
    with an explicit reason; a missing per-solve record without a reason MUST fail
    batch verification.

### Budget

28. The study MUST run under identity gpup-throughput-v1 with prefix gpupt, study cap
    2700 seconds, acceptance cap 600 seconds and combined cap 3300 seconds, inside a
    cumulative ceiling of 8102574545061 nanoseconds.
29. The protocol MUST carry its own ceiling authority: source_campaign {path, sha256}
    naming benchmarks/configs/lp-precision-v4.json, additional_gpu_seconds 3600, and
    decision {path, sha256} naming ADR-0023. Tooling MUST refuse to open the ledger when
    cumulative_ceiling_ns differs from the source campaign's cumulative_gpu_ns plus
    additional_gpu_seconds, or when the decision hash differs. The source campaign file
    itself MUST NOT be modified.
30. The protocol MUST record prior_gpu_ns 3794758955639, prior_events 6722 and
    prior_ledger_sha256
    ff6f1b5471e80791e964d1e6679017ea33593a7899718d0431f666cfaa5fa23b; tooling MUST
    revalidate the prefix before any work is admitted.
31. Cap exhaustion MUST stop the study with explicit missing-evidence records; no other
    allowance may be created. benchmarks/configs/lp-research-v1.json,
    lp-research-v2.json, lp-precision-v4.json, all manifests and all archived artifacts
    MUST remain byte-identical.

### Ownership and gates

32. Unsafe code MUST remain only in optimizer-cuda-sys (ADR-0009); no new driver-API
    symbol may be added. optimizer-lp, optimizer-lp-cuda, optimizer-experiment and
    optimizer-cli keep the unsafe prohibition.
33. An ordinary `cargo build` MUST keep working on a host with no CUDA toolkit and no
    device; nvcc remains a provisioning dependency, never a build dependency.
34. Device tests MUST stay device-gated; every session_ case MUST pass under all four
    scoped sanitizers (memcheck, racecheck, initcheck, synccheck) sequentially with zero
    errors, charged to acceptance.
35. The CLI MUST read each batch document under its existing 16 MiB per-document input
    limit; extension instances exceed it and therefore reach only the research
    executable. Documentation cross-references (SPEC-0012, SPEC-0013, the roadmap, the
    candidate register, operations, README, schemas README, wiki, AGENTS) and the
    CHANGELOG MUST be updated in the same change as the behavior.

## Interfaces

### Rust API (optimizer-lp)

```rust
impl LinearProgram {
    fn with_variable_bounds(&self, variant: &Model) -> Result<Self, ValidationError>;
    fn same_matrix_objective_rows(&self, other: &Self) -> bool;
    fn matrix_sha256(&self) -> String;
}

pub struct PreparedMatrix { /* preconditioner, settings, scaled matrix both
    orientations, scaled objective, step */ }
impl PreparedMatrix {
    pub fn new(program: &LinearProgram, settings: &LpSettings) -> Self;
}
impl<'a> Engine<'a> {
    pub fn from_prepared(program: &'a LinearProgram, prepared: &PreparedMatrix)
        -> Engine<'a>;
}
```

`Engine::new` and `with_preconditioner` are refactored to compose `PreparedMatrix::new`
and `Engine::from_prepared`, so the single-solve path exercises the same code the
session does; the existing bitwise trajectory tests pin the refactor.

### Rust API (optimizer-lp-cuda)

```rust
pub struct TunedSession { /* context, settings, execution record, base model,
    program, prepared matrix, residency, loaded bound key, poisoned flag,
    setup phases */ } // !Send
impl TunedSession {
    pub fn open(context, settings, execution, model, diagnostics)
        -> Result<Self, _>;       // admission + residency once
    pub fn solve(&mut self, variant: Option<&Model>, options, cancel,
        diagnostics: &mut LpDiagnostics) -> Result<SolveRecord, ValidationError>;
}

#[cfg(feature = "precision-research")]
pub struct ResearchSession { /* context, hashed image, base model/program,
    prepared matrix, Operator, one ResearchExecutor, poisoned flag */ }
```

Per solve the session builds a short-lived `Engine::from_prepared`, resets executor
gating (fresh TunedExecutor, or `ResearchExecutor::begin_solve`), rebinds column bounds
only when they changed (`LpResidency::rebind_column_bounds` /
`ResearchExecutor::rebind_column_bounds`, counted as `bound_rebinds`), runs the existing
matched iteration with a fresh controller from the cold iterate, and assesses and
records exactly as the single-solve path.

### CLI

```
optimizer solve-batch --model M --batch B --config C --lp-settings S \
    --lp-execution E --device D --lp-evidence DIR [--lp-profile] \
    [--lp-device-memory-bytes N]
optimizer lp-study materialize --model M --batch B --index K --out FILE
optimizer lp-study verify-batch --model M --batch B --evidence DIR
```

`solve-batch` writes DIR/solve-NNN.json (lp-endpoint-v3, one per solve, create_new +
rename) and DIR/batch.json (lp-batch-endpoint-v1). Its exit status is the worst
per-solve exit code. There is no HiGHS fallback: a session failure is reported, never
substituted. Both input documents are read under the existing 16 MiB limit.

### Research executable

```
lp_precision_research batch MODEL BATCH-REQUEST EVIDENCE-DIR
lp_precision_research verify-batch MODEL BATCH-REQUEST EVIDENCE-DIR
```

Modes are limited to intguard-fp64 and fused-fp64 — the two modes bitwise-identical to
the FP64 control. Per-solve records are research-v2 evidence documents, individually
verifiable with the existing verifier against the materialized variant bytes.

### Documents

- lp-batch-request-v1 and lp-batch-endpoint-v1: JSON Schema documents, `const`
  schema_version, additionalProperties false, validated like every other committed
  schema and example.
- Research batch request and batch evidence, version 1: Rust strict documents
  (required objects, no unknown fields, unique keys), no JSON schema, mirroring
  research-v1/v2 practice.

## State and invariants

A session owns its context handle and is !Send. Its state machine is: open (admission
and invariant upload once) → ready → per-solve (rebind → run → assess → record) →
closed, with a poisoned terminal state entered on any device fault other than
cancellation; a poisoned session refuses further solves and records them not_attempted.
The cold-iterate rule (requirement 8) is an invariant, not a setting: there is no API
to seed a solve from a previous solve's state. The residency's invariant `uploads()`
counter is 1 for the session's lifetime; per-solve working-state uploads and bound
rebinds are counted separately. Determinism follows requirement 15: identical bits,
counts and statuses against the fresh-process solve of the same materialized model.

## Errors and recovery

- Matrix/objective/row/ID mismatch between variant and session: refused before any
  allocation or upload for that solve; earlier records retained.
- Unknown variable ID in a variant change list; inverted or non-dyadic bound; variant
  request for a witness-less instance: refused at materialization or admission.
- Unsupported mode: the research batch refuses modes other than intguard-fp64 and
  fused-fp64.
- Poisoned session: subsequent solves recorded not_attempted with the fault as reason.
- Oversized document: the CLI's 16 MiB per-document limit refuses before any device
  open.
- Cancellation: observed between solves and at existing chunk boundaries; completed
  records retained; the interrupted solve maps to the existing interrupted semantics.
- Device failure within a solve: the existing solve_observed mapping applies to that
  solve's record, then the session poisons (requirement 13).

## Compatibility and versioning

All documents are new versioned kinds at version 1; no existing schema, record, request
or evidence changes meaning or bytes. lp-endpoint-v3 and research-v2 per-solve records
are embedded by reference (hash) in batch records, never modified. The source campaign,
prior protocols, manifests and archives are byte-identical (requirement 31). The batch
kinds follow the repository rule: a breaking change is a new versioned file.

## Security and resource limits

All device work runs under the shared host lease, one holder across device selections.
Memory admission happens once at session open with the existing admissibility check.
The supervisor's per-file limit (32 MiB) bounds every evidence file; the batch limit
(bounds on N and per-solve limits) is recorded in the request. GPU consumption is
bounded by requirement 28's caps inside the cumulative ceiling, with the campaign
28800-second and phase caps unchanged. The CLI keeps its 16 MiB per-document input
limit. Sessions never widen what a caller can ask of a backend beyond what the
single-solve path already allows.

## Examples

```
optimizer solve-batch --model examples/lp-model-v1.json \
    --batch examples/lp-batch-request-v1.json --config examples/search-config-v3.json \
    --lp-settings examples/lp-settings-v1.json \
    --lp-execution examples/lp-execution-v1.json \
    --device GPU-dfb2449a-9eff-e868-3597-2c448c9a8e48 \
    --lp-evidence /tmp/batch-evidence
```

Expected: /tmp/batch-evidence/solve-000.json and solve-001.json (each an
lp-endpoint-v3 record that `optimizer lp-study verify` accepts) plus
/tmp/batch-evidence/batch.json; exit status 0 when both solves certify.

## Open questions

- Warm starts across solves are excluded here; whether a bounded warm-start contract is
  worth a later specification is open and belongs to the GPUP-6 interface discussion.
- `Model::rebound` clones the full variable vector per variant; at 65536 rows this
  clone cost is measured (variant_rebind phase) rather than optimized in this slice.
